# Core-flow contract

This document is the cross-repository contract for the Elera application flow.
The implementation is intentionally split between supervisor, CLI, and client
library; this file records the shared object and authorization semantics.

## Resource identity

Applications, app-admin tokens, databases, identities, SQL credentials, runtime
tokens, and operations have Snowflake IDs. Friendly names are labels only.
Physical database and SQL-user names are generated by the supervisor from those
IDs and are never selected by applications.

## Token resolution

An app-admin token is scoped to exactly one application and may manage only its
application resources. A runtime token resolves directly to:

`application + database + identity + scopes`

Each runtime token represents one database context. An application needing two
databases uses two runtime tokens. Root credentials are platform-only and are
never passed to application workloads.

## Application contract

Applications configure only:

```text
ELERA_API_ENDPOINT
ELERA_API_TOKEN
```

The client library obtains the routing bundle and physical SQL credentials
using that token. Applications do not provide application, database, identity,
SQL username, SQL password, node, or cluster settings.

## Routing bundle

The supervisor returns the resolved application, database, identity, resource
IDs, credentials, writer, readers, ordered failover nodes, bundle version,
expiry, node identity, and port data. Routing changes are delivered through
the WebSocket event stream, with REST bundle retrieval as the recovery path.

## Authorization boundary

Root-only operations include initialization, bootstrap, recovery, node
lifecycle, draining, cluster configuration, secrets, and platform backup or
restore. App-admin operations are limited to application resources, including
databases, identities, runtime tokens, routing inspection, and application
telemetry.
